# mk61emu

```sh
cmake --preset gui-local
cmake --build --preset gui-local
ctest --preset gui-local
cmake --preset gui-release-local
cmake --build --preset gui-release-local
```

[English](README.md) | Українська

Невеликий шаблон проєкту на C++23 з основною бібліотекою, консольним застосунком
і тестами на Catch2. Без налаштувань CI та залежностей під конкретний застосунок.
У `apps/gui` також є опційний застосунок на Qt Widgets.

## Вимоги

- CMake 3.25 або новіший, Ninja та Git.
- Компілятор і стандартна бібліотека з підтримкою C++23, зокрема `<format>`
  та `<print>`. Самого вибору стандарту C++23 недостатньо, якщо бібліотека ще
  не реалізує потрібні можливості. Поточну конфігурацію перевірено з GCC 16
  і libstdc++ 16 на Linux; інші поєднання компілятора й бібліотеки потрібно
  перевірити перед використанням.
- За потреби: clangd, clang-format і clang-tidy, сумісні з вибраним компілятором
  та стандартною бібліотекою. Інструменти перевірено у версії 22.

Якщо тести ввімкнено, Catch2 v3.5.2 завантажується під час конфігурування.
Перше конфігурування потребує доступу до мережі. Щоб використати вже наявну
локальну копію вихідного коду Catch2, передайте
`-DFETCHCONTENT_SOURCE_DIR_CATCH2=/absolute/path/to/Catch2`.

## Збірка й тести

```sh
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
./build/dev/apps/cli/mk61emu

cmake --preset release
cmake --build --preset release
```

У release-збірці тести за замовчуванням вимкнено. Обидва пресети використовують
Ninja, тому у Windows потрібне налаштоване середовище компілятора, наприклад
термінал розробника Visual Studio.

## Перевірки

```sh
cmake --build build/dev --target format-check
cmake --build build/dev --target format

cmake --preset sanitized
cmake --build --preset sanitized
ctest --preset sanitized

cmake --preset analyze
cmake --build --preset analyze
ctest --preset analyze
```

Ціль `format` форматує C++-файли проєкту, а `format-check` лише перевіряє їх.
Ці цілі доступні, якщо clang-format знайдено під час конфігурування.
Згенеровані файли та завантажені залежності не форматуються.

Пресет `sanitized` вмикає ASan і UBSan для цілей проєкту. Він потребує GCC
або Clang на Unix-подібній платформі та відповідних бібліотек виконання
санітайзерів. Ці налаштування не додають інструментацію до сторонніх залежностей.
TSan не включено: його варто додати окремо, коли з'явиться багатопотоковий код.

Пресет `analyze` потребує clang-tidy та перевіряє цілі проєкту, а не власні
вихідні файли Catch2. Зауваження ввімкнених перевірок clang-tidy зупиняють збірку.
Щоб явно вказати потрібний інструмент, передайте
`-DCLANG_TIDY_EXECUTABLE=/path/to/clang-tidy` або
`-DCLANG_FORMAT_EXECUTABLE=/path/to/clang-format` і повторіть конфігурування.

Параметри проєкту можна змінювати через `-DNAME=ON` або `-DNAME=OFF`:

| Параметр                    | Типово | Призначення                                |
| --------------------------- | ------ | ------------------------------------------ |
| `BUILD_APPS`                | ON     | Збирати консольний застосунок              |
| `BUILD_GUI`                 | OFF    | Збирати опційний застосунок Qt Widgets     |
| `BUILD_TESTS`               | ON     | Завантажувати Catch2 і збирати тести       |
| `ENABLE_WARNINGS_AS_ERRORS` | OFF    | Вважати попередження компілятора помилками |
| `ENABLE_SANITIZERS`         | OFF    | Увімкнути ASan і UBSan                     |
| `ENABLE_CLANG_TIDY`         | OFF    | Аналізувати код проєкту під час компіляції |

Пресети `sanitized` та `analyze` також вмикають обробку попереджень як помилок.
Для тестів проєкту діє базовий набір попереджень, для бібліотеки й консольного
застосунку також увімкнено суворіші перевірки. Під час компіляції власних файлів
Catch2 попередження вимкнено (`-w` або `/w`), а його заголовки вважаються системними.

## Опційний застосунок Qt Widgets

Qt шукається лише за умови `BUILD_GUI=ON`. Бібліотека, CLI та тести не залежать
від Qt; опції `BUILD_APPS` і `BUILD_GUI` незалежні. Установіть комплект розробки
Qt 6 із модулем Widgets та інструментами moc/uic/rcc. У Debian та Ubuntu системний
пакет для розробки зазвичай називається `qt6-base-dev`. Проєкт не завантажує Qt
автоматично.

Для системного встановлення:

```sh
cmake --preset gui
cmake --build --preset gui
ctest --preset gui
./build/gui/apps/gui/mk61emu-gui
```

Шлях запуску наведено для Linux. У Windows виконуваний файл має суфікс `.exe`,
а в macOS він розміщений усередині пакета застосунку. Приклад показує привітання
з основної бібліотеки й оновлює його після зміни імені.

Для комплекту Qt, встановленого в довільному каталозі:

```sh
cmake --preset gui -DCMAKE_PREFIX_PATH="$HOME/Qt/6.12.0/gcc_64"
cmake --build --preset gui
```

`CMAKE_PREFIX_PATH` вказує на корінь установленого комплекту, а не на його
каталог `include` чи `bin`. CMake знаходить конфігурацію пакетів Qt та імпортовані
цілі, які надають шляхи до заголовків, бібліотек та інструментів. Альтернатива:
`-DQt6_DIR="$HOME/Qt/6.12.0/gcc_64/lib/cmake/Qt6"`. Зазвичай достатньо лише одного
з цих налаштувань. Версія та шлях у прикладі не є вимогою проєкту.

Щоб не додавати локальний шлях до спільної конфігурації, створіть у корені
проєкту ігнорований `CMakeUserPresets.json` або додайте цей пресет до наявного:

```json
{
    "version": 3,
    "configurePresets": [
        {
            "name": "gui-local",
            "inherits": "gui",
            "cacheVariables": {
                "CMAKE_PREFIX_PATH": "$env{HOME}/Qt/6.12.0/gcc_64"
            }
        }
    ],
    "buildPresets": [{ "name": "gui-local", "configurePreset": "gui-local" }]
}
```

Використовуйте `cmake --preset gui-local` і `cmake --build --preset gui-local`.
Приклад успадковує каталог `build/gui`, тому налаштування clangd для GUI
працюватиме без змін. Для іншого комплекту Qt, архітектури чи компілятора
використовуйте окремий каталог збірки та відповідно змініть шлях до бази команд
GUI в `.clangd`. Не змішуйте системні компоненти Qt з компонентами іншого
комплекту. Комплект має відповідати платформі, архітектурі та сумісному
компілятору й ABI.

GUI підключає лише `Qt6::Widgets`, який також підтягує `Gui` та `Core`.
Для іншого модуля встановіть його до того самого комплекту Qt, додайте його назву
до `find_package(Qt6 REQUIRED COMPONENTS Widgets Network)` і підключіть відповідну
ціль, наприклад `Qt6::Network`, у `apps/gui/CMakeLists.txt`. Підключати всі модулі
Qt не потрібно.

Лише для GUI ввімкнено `AUTOMOC` (для `Q_OBJECT`, сигналів і слотів), `AUTOUIC`
(для включених згенерованих заголовків форм) та `AUTORCC` (для ресурсів).
Додавайте власні заголовки, форми `.ui` та ресурси `.qrc` до `qt_add_executable`
у міру їх появи. Генерація коду Qt не впливає на основну бібліотеку чи Catch2.
Пресет `gui` запускає наявні тести основної бібліотеки; автоматизованих GUI-тестів
він не додає. Для поширення застосунку на інші комп'ютери потрібні також
бібліотеки виконання та плагіни Qt, зокрема плагін платформи; шаблон поки
не реалізує розгортання.

## Налаштування редактора

Установіть розширення clangd і сам clangd версії 22 або новішої. Спільні
налаштування вибирають `clangd-22` за назвою виконуваного файла, без абсолютного
шляху встановлення. Якщо у вашій системі він має іншу назву, наприклад `clangd`,
змініть `clangd.path` у `.vscode/settings.json`. Не додавайте до комітів абсолютні
шляхи, прив'язані до конкретної машини.
Clangd 18 видає хибні діагностики з libstdc++ 16 у поточній конфігурації проєкту.
Спільні налаштування вимикають паралельний рушій Microsoft C++ IntelliSense;
розширення Microsoft при цьому можна й далі використовувати для налагодження.

Перед відкриттям C++-файлів виконайте `cmake --preset dev`. Конфігурація `.clangd`
читає шляхи до заголовків і прапорці компілятора з `build/dev/compile_commands.json`.
Для `apps/gui` використовується `build/gui/compile_commands.json`; перед
редагуванням GUI виконайте конфігурування з пресетом `gui` або `gui-local`.
Додавати шляхи до заголовків Qt вручну чи використовувати заглушки не потрібно.
Після зміни набору інструментів повторіть конфігурування та виконайте команду
**clangd: Restart language server**. Якщо GCC встановлено нестандартним способом,
додайте до `clangd.arguments` у користувацьких налаштуваннях
`--query-driver=/absolute/path/to/compiler`, дозволивши лише потрібний компілятор.

Локальні налаштування компіляторів, шляхи до інструментів і пресети зберігайте
в `CMakeUserPresets.json`, який ігнорується Git. Для кожного набору інструментів
використовуйте окремий каталог збірки. Якщо редактор має аналізувати іншу збірку,
відповідно змініть `.clangd`.

## Адаптація шаблону

### Створення копії проєкту

Запустіть генератор із цього шаблону через Python 3.9 або новіший.
Додаткових Python-пакетів не потрібно:

```sh
python3 scripts/create_project.py
```

Скрипт запитає каталог, назву проєкту, простір імен C++, версію, тип застосунку,
чи потрібні тести, шлях до Qt, компілятор і чи перевіряти збірку. Усе це також
можна передати параметрами:

```sh
python3 scripts/create_project.py ../WeatherDesk --name WeatherDesk \
   --namespace weather --version 1.0.0 --kind both \
   --qt-prefix '$env{HOME}/Qt/6.12.0/gcc_64' --verify
```

`--kind` приймає `cli` (типово), `gui`, `both` або `library`. Тести типово
ввімкнено; `--no-tests` вимикає їх і завантаження Catch2.
`--cxx-compiler /path/to/g++` вибирає компілятор. Додаткові локальні змінні CMake
передавайте повторюваним `--cache KEY=VALUE`, наприклад
`--cache ENABLE_WARNINGS_AS_ERRORS=ON` або
`--cache FETCHCONTENT_SOURCE_DIR_CATCH2=/path/to/Catch2`. Режим збірки задавайте
через `--kind` і `--tests`, а не `--cache`. Для системного Qt не вказуйте
`--qt-prefix`. Макроси CMake беріть в одинарні лапки, як у прикладі;
`~/Qt/...` у пресетах не розгортається, тож використовуйте абсолютний шлях
або `$env{HOME}`.

Каталог призначення має бути новим і розташованим поза шаблоном. Генератор
копіює вихідний код і налаштування редактора, змінює назву CMake-проєкту,
псевдонім основної бібліотеки, простір імен C++, заголовок вікна, назви
виконуваних файлів і типові параметри збірки. Для `both` застосунки матимуть
назви `WeatherDesk` і `WeatherDesk-gui`. Вимкнені компоненти залишаються у
вихідному коді. Історія Git, каталоги збірки, наявні локальні пресети та власні
скрипти й тести генератора не копіюються. Початковий шаблон не змінюється;
щоб створити ще один проєкт, знову запустіть генератор із шаблону.

У копії створюється ігнорований Git файл `CMakeUserPresets.json` із пресетами
конфігурування та збірки: `dev-local` і `release-local` або `gui-local` і
`gui-release-local` для GUI. Шляхи до Qt й вибір компілятора записуються лише
до цього локального файла. Для Debug із тестами додається відповідний тестовий
пресет; Release збирається без тестів. На початку README копії будуть команди
для вибраних пресетів, а clangd використовуватиме відповідну Debug-базу.
На іншій машині локальні пресети потрібно відтворити, бо Git їх ігнорує.

`--verify` конфігурує та збирає обидва локальні пресети, запускає ввімкнені
Debug-тести й повертає ненульовий код у разі помилки. Потрібні CMake, Ninja,
відповідний компілятор C++23, Qt для GUI, а для тестів також мережа або локальна
копія Catch2. Якщо перевірка не вдалася, створений проєкт залишається для
діагностики: виправте його на місці або виберіть новий каталог для генерації.

Перевірки генератора, зокрема опційні справжні збірки й запуск GUI без екрана:

```sh
python3 -m unittest discover -s tests -p test_create_project.py -v
CPP_STARTER_INTEGRATION=1 CPP_STARTER_QT_PREFIX="$HOME/Qt/6.12.0/gcc_64" \
   python3 -m unittest discover -s tests -p test_create_project.py -v
```

### Подальша робота з кодом

1. Якщо адаптуєте шаблон вручну, перейменуйте `mk61emu`, `mk61emu::Core`
   і простір імен `mk61::core`. Генератор уже виконує цей крок.
2. Замініть приклади Greeter, консольного застосунку й тесту кодом свого проєкту.
3. Зберігайте заголовки бібліотеки в `libs/core/include`, реалізацію в
   `libs/core/src`, виконувані застосунки в `apps`, а тести в `tests`.
4. Підключайте до нових цілей проєкту `Project::Options`, `Project::Warnings`
   і, за потреби, `Project::StrictWarnings`. Додавайте назви нових цілей до списку
   перевірки clang-tidy в кореневій конфігурації CMake.
5. Виберіть ліцензію та задокументуйте підтримувані версії компіляторів
   і стандартних бібліотек. Оновлюйте цей README разом зі змінами команд і вимог.

Правила встановлення й експорту цілей, пакування, звіти про покриття тестами,
бенчмарки, генерацію документації API, додаткові менеджери залежностей,
логування та розбір аргументів командного рядка залишено для окремих проєктів.
